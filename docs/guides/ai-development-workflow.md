# AI Development Workflow Guide

## 1. Overview

This guide defines how AI tools are used throughout the GooglePay-AI-Checkout project. The core philosophy is:

- **Context Engineering > Prompt Engineering** — The quality of AI output depends more on the context provided (documentation, existing code, ADRs, API schemas) than on clever prompt wording.
- **MCP grounds AI in real API data** — The Google Pay MCP Server ensures AI tools generate code against the actual API surface, not memorized (potentially outdated) training data.

AI tools are collaborators, not autonomous agents. Every AI-generated artifact passes through human review before merge.

## 2. Tool Selection

Choose the appropriate AI tool based on the task type:

| Tool | Primary Use Cases |
|------|-------------------|
| **Antigravity** | Google Pay MCP Server interaction, codelab implementation |
| **Kiro** | Architecture decisions, project planning, spec-driven development |
| **OpenHands** | Backend coding, complex implementation tasks |
| **ChatGPT** | Research, code review, documentation review |
| **Copilot** | Inline code completions, small refactors |

**Selection Criteria:**
- Use MCP-grounded tools (Antigravity) for any Google Pay API work.
- Use architecture-aware tools (Kiro) for structural decisions.
- Use coding-focused tools (OpenHands, Copilot) for implementation.
- Use general-purpose tools (ChatGPT) for research and review.
- Follow ADR-003 for detailed orchestration rules.

## 3. Workflow Steps

Every AI-assisted development task follows this sequence:

### a. Define Objective (Human)

The human developer writes a clear, one-sentence objective before engaging any AI tool.
This ensures intentional use rather than exploratory wandering.

### b. Gather Context (MCP + Codebase)

Before generating anything, gather:
- Relevant MCP documentation (API schemas, endpoint specs)
- Existing code that touches the same domain
- Applicable ADRs and architectural constraints
- Test expectations and acceptance criteria

### c. Select Appropriate AI Tool (per ADR-003)

Based on the task type, select the tool best suited to the job (see Tool Selection table above).

### d. Generate Implementation

Feed the gathered context into the selected tool with a structured prompt (see Prompt Engineering Guide). Capture the full interaction for the AI Interaction Log.

### e. Second AI Tool Reviews (Arbitration Protocol)

A different AI tool reviews the generated output for:
- Correctness against the gathered documentation
- Security concerns
- Adherence to project conventions
- Potential hallucinations or fabricated API surfaces

### f. Human Review + Manual Edits

The human developer:
- Reviews the generated code for correctness and intent alignment
- Makes manual edits as needed
- Documents reasons for any changes in the AI Interaction Log

### g. Automated + Manual Testing

- Run all applicable automated tests (unit, integration, e2e)
- Perform manual testing for UI/UX concerns
- Verify against acceptance criteria defined in step (a)

### h. Merge with AI Interaction Log Entry

Before merging:
- Ensure AI Interaction Log entry is complete
- Confirm all tests pass
- Obtain required code review approvals

## 4. MCP Integration

### How to Use the Google Pay MCP Server

The MCP (Model Context Protocol) server provides real-time access to Google Pay API documentation and schemas.

**Workflow:**
1. Before generating any Google Pay-related code, retrieve the relevant documentation via MCP.
2. Include retrieved docs in the AI tool's context window.
3. Never rely on memorized API surfaces — they may be outdated or hallucinated.
4. If the MCP server is unavailable, **pause feature work** rather than guessing at API shapes.

**Key Principles:**
- MCP docs are the single source of truth for API contracts.
- Re-fetch documentation at the start of each development session.
- Cache retrieved docs locally for offline reference, but always prefer fresh data.
- Log which MCP documents were retrieved in the AI Interaction Log.

## 5. AI Interaction Log Format

**Location:** `docs/ai-log/YYYY-MM-DD-<feature-slug>.md`

Each log entry must include the following fields:

| Field | Description |
|-------|-------------|
| **Prompt** | The exact prompt or instruction given to the AI tool |
| **AI Tool** | Which tool was used (Antigravity, Kiro, OpenHands, ChatGPT, Copilot) |
| **Documentation Retrieved** | MCP docs, ADRs, or other context provided |
| **Generated Diff** | The raw output / code generated by the AI |
| **Manual Edits** | Changes made by the human after generation |
| **Reason for Edits** | Why each manual edit was necessary |
| **Test Result** | Pass/fail status of automated and manual tests |
| **Final Result** | Accepted, rejected, or partially accepted |

## 6. Arbitration Protocol

When two AI tools produce conflicting recommendations:

1. **Log the disagreement** — Record both outputs and the specific conflict in the AI Interaction Log.
2. **Human decides** — The human developer evaluates both recommendations against project constraints, documentation, and ADRs.
3. **Record as ADR if structural** — If the disagreement reveals an architectural decision point, create a new ADR to document the decision and rationale.

This ensures no AI tool has unilateral authority over project direction.
